Migrations apply in version order: `001` → `006`, then the timestamped ones (the CLI sorts them the same way).

Choir-specific rules worth knowing:

- `choir_rota_song_selections.section` splits a date's set list into `praise` and `worship`. RLS lets the assigned **Praise Leader** manage praise rows, the **Worship Leader** manage worship rows, a legacy **Song Leader** manage both, and the choir team leader / church admin manage everything (`can_manage_song_section()` in migration 004).
- `rota_entries.status` marks cancelled dates (e.g. a called-off rehearsal) instead of deleting them; cancelling is a plain update already covered by the leaders-manage-rota policy. Members keep updating only their own `availability_responses`.
- A choir rehearsal is just a rota entry where every choir member has a `'Choir Member'` assignment — availability tracking needs no extra tables.

## Design in one paragraph

The deployed identity foundation distinguishes Supabase `auth.users`, one account-global `user_accounts` row, and stable organisation-scoped `profiles` rows. One Auth user may own one profile per organisation; `user_accounts.active_profile_id` is ownership-validated and `current_profile_id()` scopes normal RLS queries to that single organisation. The local membership migration adds `profiles.access_status`: removed profiles keep their IDs and historical attribution but grant no access. Effective display name is `profiles.display_name_override ?? user_accounts.global_display_name`, while synchronized `profiles.full_name` preserves existing readers. Demo/mock data remains separate.

### Deployed organisation membership and role management

`20260712103321_add_organisation_membership_role_management.sql` is deployed (2026-07-12). It adds explicit `active`/`removed` organisation access with removal audit fields and replaces active-profile/account helpers so removed profiles cannot be current, listed as account access, switched to, or added to a team. Profiles, global accounts, Auth users, other organisations, messages, authored content, rota assignments, availability, read cursors, preferences, invitation history, and delivery history are retained.

The authenticated app surface is four narrow RPCs:

- `list_organisation_members(p_search, p_limit)` — church-admin-only bounded read model; no Auth IDs, invitation hashes, or push tokens.
- `set_organisation_member_role(p_profile_id, p_role)` — replaces the target's one schema-supported role.

- `leave_organisation()` — caller-owned departure with no caller/profile/organisation argument.

Role change, admin removal, and self-leave lock the same organisation row before counting effective linked active `church_admin` profiles, so concurrent operations cannot leave zero admins. Team addition and push registration lock the target profile before writing, serializing them with removal cleanup so they cannot recreate stale access or delivery endpoints. Remove/leave deletes current organisation roles, team memberships, and profile-owned push tokens, then marks the stable profile removed; active profile is selected automatically for one remaining organisation, cleared for the selector when several remain, or cleared for no-organisation state. Every removal touches the target account's owner-RLS `user_accounts` row, including non-active-organisation removal, so shared Postgres Changes invalidation clears and remounts its old AppData/channels promptly; the deployed publication now carries 14 tables (the original 13 plus `user_accounts` exactly once), and the chat tables remain absent under the private Broadcast architecture.

Removed profiles can be invited again through the existing Edge Function. Acceptance requires the same matching verified Auth account, reactivates the same profile ID, clears removal audit fields, defensively removes stale roles/teams/tokens, and inserts `general_member` only. Active unlinked directory profiles retain the existing first-invitation behavior.

Direct authenticated profile/role writes remain revoked and the old permissive role-write policy is dropped. Every new definer function has `search_path = ''`, fully qualified relations, server-derived caller/tenant authority, and explicit ACLs. The current deterministic suite passes 565 tests across 61 suites.

### Team creation and archive lifecycle

`20260715004513_add_team_creation_editing_and_archive.sql` implements Team Creation & Editing V1 and is deployed to `shift-shepherd-dev`. It adds nullable `teams.archived_at` and `teams.archived_by`, with `archived_by` referencing `profiles(id) ON DELETE SET NULL`, plus partial organisation-scoped indexes for active and archived directory reads.

The authenticated app surface is four table-shaped `SECURITY DEFINER` RPCs with empty search paths and explicit authenticated-only ACLs:

- `create_team(p_name, p_description, p_initial_admin_profile_id)` derives the active profile/organisation, requires the existing `church_admin` organisation role, creates an active generic team, and accepts no caller or organisation authority argument. A null initial admin creates no membership. One explicitly selected active linked profile in the same organisation receives exactly one existing `team_leader` membership atomically; the creator is not otherwise added.
- `update_team(p_team_id, p_name, p_description)` edits active-team identity only.
- `archive_team(p_team_id)` locks the same organisation team row and records server time/caller attribution without deleting child data.
- `restore_team(p_team_id)` clears both archive fields on that same row.

Active-team helper functions now exclude archived teams, so ordinary directories, memberships, chat, rota, choir/song, member-add, leave-team, unread-summary, and avatar mutation paths cannot use an archived team. Church admins retain organisation-scoped archived metadata needed to identify and restore it. Archive preserves the team ID, memberships, chat/read state, rota/assignments/availability, songs/links/selections, avatar path/object, attribution, and every other foreign-key relationship. Existing team-avatar authorization already permits same-organisation church admins, so storage policy scope was not broadened. Teams intentionally may have zero team admins.

### Team creation idempotency (deployed; hosted-contract verified; manual app QA pending)

`20260917093926_add_team_creation_idempotency.sql` implements Team Creation Idempotency V1 and was applied to `shift-shepherd-dev` on 2026-09-17 as the only remote mutation of its deployment task. It adds nullable `teams.create_request_id uuid` and nullable `teams.create_request_initial_admin_id uuid` (the keyed request's initial-admin argument, recorded without a foreign key so a replay is always compared against what was originally asked for) with the partial unique index `teams_organisation_create_request_id_key (organisation_id, create_request_id) where create_request_id is not null`, drops `create_team(text, text, uuid)`, and recreates `create_team(p_name, p_description, p_initial_admin_profile_id, p_request_id uuid)` with the same table-shaped response, hardening (`SECURITY DEFINER`, `search_path=''`, schema-qualified), server-derived authority, and authenticated-only ACL. A null `p_request_id` raises `INVALID_REQUEST_ID`. After every authority and validation check, and under the existing organisation-row lock (which already serializes every create in the organisation), the function looks up `(organisation_id, create_request_id)` for the caller's own organisation only: on a hit it locks the team row, verifies that the stored name/description match the request and that the stored initial-admin argument equals the replayed one in both directions (no admin vs an admin, or a different admin, is `CREATE_REQUEST_MISMATCH`), fetches that stored admin's membership (missing is also a mismatch), and returns the existing team and existing membership without inserting anything; otherwise it inserts the team with the key and the argument. A key reused by another organisation never resolves that organisation's team; it simply keys a new team there. Team names remain non-unique, historical teams keep a null key, `unique_violation` maps to `CONFLICT_RETRY`, and no policy, trigger, publication, helper, or existing row changes. The client mints one UUID per logical submission, reuses it across retries of the same draft, rotates it when the draft changes or a conflict is reported, and rejects malformed keys before any network call. Static contract tests pin the migration and verify all 33 earlier migration bytes unchanged. Hosted verification on 2026-09-17 confirmed the deployed body is byte-identical to the migration (single `create_team(text, text, uuid, uuid)` overload, `SECURITY DEFINER`, `search_path=''`, owned by `postgres`, EXECUTE for `authenticated` only with none for `anon`, `service_role`, or `PUBLIC`), both nullable columns without a foreign key, the exact partial unique index, and unchanged policy/trigger/publication counts and RLS. ## Push delivery: chat messages, announcements, and rota updates (deployed)

Push delivery is server-side only — the app never talks to Expo's push API itself. After a live write succeeds, the app makes one best-effort, fire-and-forget call to the `send-chat-message-push` Edge Function with exactly one of `{ messageId }` after a chat send, `{ announcementId }` after an announcement is posted, or `{ rotaEntryIds }` after a rota save (see `src/lib/supabase/services/pushDelivery.ts`); send/post UX is never blocked by delivery. The function re-validates everything against the database using the service role (which exists only in the Edge Function runtime):

- the caller holds a valid user JWT (`verify_jwt` is on) and resolves to the server-validated active profile of their account;
- chat (deployed, unchanged): the message exists, the caller is its sender, it is at most five minutes old, and the caller can access the team (membership or church admin); recipients are the team's other members with `notification_preferences.chat_notifications` enabled (a missing row means the app's all-on defaults) and at least one registered push token; the sender is never notified.
- announcements (Announcement Push Delivery V1, **deployed 2026-09-17 as v6; hosted-contract verified**): the announcement exists, the caller is its author in the same organisation, and it is at most five minutes old; a team announcement additionally requires an active (non-archived) team. Recipients mirror the announcements SELECT policy — every active, linked profile of the organisation for a church-wide announcement, and the team's members (active, linked, same organisation) for a team announcement — filtered by the existing `announcement_notifications` (church-wide) or `team_announcement_notifications` (team) preference. The author is never notified, church admins who are not members of a team are not notified about that team's announcements (matching the chat convention), removed profiles are excluded (they also hold no tokens), and each profile is notified at most once however it is reachable. Editing an announcement never re-notifies; only the create path calls.
- rota updates (Rota Push Delivery V1, **deployed 2026-09-17 as v7; hosted-contract verified**): the app sends `{ rotaEntryIds }` (1–50 ids) once per live logical save — one entry create or edit, one cancel or restore, or one whole Plan the Month batch. Every entry must exist in the caller's organisation and belong to one active (non-archived) team, and the caller must be able to manage that rota (team leader or church admin, mirroring `can_manage_team`). Recipients are the people on those entries who are active, linked, same-organisation current members of the team, filtered by the existing `rota_notifications` preference; the caller is never notified. Two event kinds share the ledger: `rota_assignment` (event id = `rota_assignments.id`) for each assignment row created in the last five minutes, notifying its assignee, and `rota_entry_change` (event id = `rota_entries.details_change_id`) when the entry's title, date, time, notes, or cancellation status changed in the last five minutes, notifying the people whose assignment already existed before that change (people added by the same save get the "added" event instead). Every row newly claimed for one device in one request becomes a single notification ("New rota assignment" / "You have been added to the <Team Name> rota.", "Rota updated" / "A date you are on in the <Team Name> rota has changed.", or a combined "Your dates on the <Team Name> rota have been updated.") with `data: { type: 'rota', teamId, rotaEntryId? }`. Deleted entries, removed assignments, availability responses, and song selections notify nobody; `event_reminders` and `availability_reminders` are not delivered: they await a product decision on timing, cadence, and audience plus approval of scheduled invocation.

Idempotency comes from the `push_notification_deliveries` ledger (migration `20260710234443`): each (event_type, event_id, recipient, token) attempt is claimed with `ON CONFLICT DO NOTHING` on a `NULLS NOT DISTINCT` unique index, so duplicate calls can never double-send. Outcomes (sent + Expo ticket id, failed + safe error code, skipped + reason) are recorded per row; app roles have **no** access to the ledger, and push tokens are never logged or returned. Notifications are deliberately generic — chat: "New team message" / "You have a new message in <Team Name>." with `data: { type: 'chat_message', teamId, messageId }`; team announcement: "New team announcement" / "A new announcement was posted in <Team Name>." with `data: { type: 'announcement', announcementId, teamId }`; church-wide: "New church announcement" / "A new announcement was posted for <Organisation Name>." with `data: { type: 'announcement', announcementId }`. Message text, announcement title/body, image details, and author names are never included (the function never even selects announcement text). The pure rules (request parsing, recipient resolution, preference suppression, dedupe, ledger-claim shapes, content) live in `supabase/functions/send-chat-message-push/dispatch.ts` and are unit-tested from the app's Jest suite. There are no push-sending triggers, cron, queues, receipts polling, or other event types (the rota change-marker trigger below only stamps `rota_entries` rows).

## Auth user to profile linking

`20260709233705_link_auth_users_to_existing_profiles.sql` introduced the historical email auto-link behavior. The deployed forward migration deliberately drops that trigger and global uniqueness without editing history. It backfills every existing linked Auth user into `user_accounts`, preserves every profile ID and visible name, chooses the oldest `(created_at,id)` profile as the deterministic active profile, and allows at most one profile per Auth user per organisation.

After the new migration is deployed, Auth signup creates only a `user_accounts` shell. Email match alone never grants organisation access. New links occur only inside row-locked invitation acceptance after a matching verified Auth email, or the no-org user creates their own organisation transactionally. Never reintroduce direct authenticated `profiles.auth_user_id` writes or the old trigger.
